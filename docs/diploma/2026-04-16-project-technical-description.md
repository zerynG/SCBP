# Техническое описание информационной системы IQNIX SCBP

> **Назначение документа.** Настоящий документ представляет собой подробное техническое описание разработанной информационной системы «IQNIX SCBP» (System for Calculating Business Project Price). Материал подготовлен как исходный источник данных для формирования выпускной квалификационной работы (бакалавра) по направлению подготовки **09.03.03 «Прикладная информатика»** в соответствии с требованиями ГОСТ 7.32-2017 и ГОСТ 7.1-2003. Документ содержит предметную область, функциональные и нефункциональные требования, технологический стек, архитектуру, модель данных, математическую модель, алгоритмы, описание интерфейса, конфигурацию и сведения о развёртывании.

## Раздел 1. Общие сведения о проекте

### 1.1. Наименование и условное обозначение

- **Полное наименование:** Информационная система расчёта стоимости бизнес-проектов «IQNIX SCBP».
- **Условное обозначение:** SCBP (*System for Calculating Business Project Price*).
- **Владелец/разработчик:** компания IQNIX (iqnix.tech).
- **Адрес промышленного развёртывания:** https://scbp.iqnix.tech.

### 1.2. Назначение

Система предназначена для автоматизации процесса формирования сметной стоимости проектов в сфере услуг и системной интеграции. Она позволяет менеджеру проекта (руководителю, коммерческому директору) рассчитать полную себестоимость проекта на основе трудоёмкости привлекаемых ресурсов (штатных сотрудников, внешних исполнителей, подрядных организаций и оборудования) и сформировать на её основе итоговую отпускную цену с учётом налогов и маржинальности.

### 1.3. Область применения

Сфера применения системы — организации, выполняющие проекты, себестоимость которых формируется из комбинации:

1. Труда штатных сотрудников на окладной форме оплаты.
2. Труда внешних исполнителей по договору ГПХ (гражданско-правовой) или режиму НПД (налог на профессиональный доход, самозанятые).
3. Услуг сторонних подрядных организаций (юридических и физических лиц).
4. Использования специализированного оборудования с различными тарифами (месяц / час / минута).

### 1.4. Цели автоматизации

- Унификация методики расчёта себестоимости и отпускной цены проектов.
- Сокращение времени подготовки коммерческого предложения с нескольких часов до единиц минут.
- Исключение расчётных ошибок, возникающих при ручном ведении смет в электронных таблицах.
- Централизованное хранение истории проектов, их ресурсов и расчётов.
- Автоматическое формирование пакета сопроводительных документов (коммерческое предложение, нормативно-методический акт) в форматах PDF / DOCX / XLSX.
- Визуальное планирование занятости персонала при помощи диаграммы Ганта.

### 1.5. Задачи системы

1. Ведение реестра проектов организации.
2. Ведение реестра ресурсов, привязанных к проекту.
3. Учёт налоговой ставки и маржинальности на уровне проекта и отдельного ресурса.
4. Расчёт количества рабочих дней по производственному календарю Российской Федерации (с учётом официальных праздников и переносов выходных).
5. Расчёт себестоимости, стоимости с маржой и итоговой цены с налогом по каждому ресурсу и по проекту в целом.
6. Учёт занятости сотрудников на других проектах и их отсутствий (отпуск, больничный) посредством модуля расписания.
7. Формирование отчётных документов.
8. Разграничение доступа пользователей.

### 1.6. Пользователи системы

| Роль | Функции |
|---|---|
| Администратор | Управление пользователями, системный справочник услуг, настройка параметров через Django-админку. |
| Менеджер проектов | Создание проектов, добавление ресурсов, ввод дат, пересчёт стоимости, генерация документов. |
| Руководитель | Просмотр реестра проектов, анализ себестоимости и маржинальности, экспорт данных. |

### 1.7. Ключевые проблемы, решаемые системой

- Ручной расчёт себестоимости в Excel приводит к ошибкам при учёте частичной занятости сотрудников (работа не полный месяц).
- Несогласованность учёта производственного календаря — разные шаблоны считают число рабочих дней по-разному.
- Необходимость повторного ввода одних и тех же данных в документы разных форматов (Word, Excel, PDF).
- Отсутствие единого источника правды по занятости специалистов между проектами.

## Раздел 2. Предметная область

### 2.1. Бизнес-процесс «Расчёт стоимости проекта»

#### 2.1.1. Модель «как есть» (AS-IS)

До внедрения системы процесс выглядел следующим образом (последовательно выполняемые функции):

1. Менеджер получает техническое задание от заказчика.
2. Менеджер самостоятельно в электронной таблице (MS Excel / Google Sheets) формирует список необходимых ресурсов.
3. Менеджер вручную определяет количество рабочих дней между двумя датами, учитывая выходные и государственные праздники.
4. По каждому ресурсу формируется отдельная формула расчёта.
5. Итоговая сумма по проекту переносится вручную в шаблон Word для коммерческого предложения и в шаблон Excel для калькуляции.
6. При любом изменении параметров весь расчёт выполняется заново.

Недостатки модели AS-IS: трудоёмкость, подверженность человеческим ошибкам, отсутствие версионности, невозможность массового анализа портфеля проектов.

#### 2.1.2. Модель «как должно быть» (TO-BE)

После внедрения системы процесс протекает так:

1. Менеджер авторизуется в системе.
2. В модуле «Проекты» создаёт карточку нового проекта, указывая заказчика, даты, налоговую ставку, маржинальность.
3. В карточке проекта добавляет необходимые ресурсы через соответствующие формы.
4. Система автоматически рассчитывает себестоимость каждого ресурса и проекта в целом с учётом производственного календаря и параметров расписания.
5. Менеджер открывает сводную таблицу и при необходимости переопределяет параметры отдельных ресурсов (услуга, даты работ, маржа ресурса).
6. Менеджер генерирует комплект документов одним нажатием кнопки и получает PDF / DOCX / XLSX.

### 2.2. Типы ресурсов проекта

#### 2.2.1. Сотрудники (Employee)

Штатные работники организации, получающие фиксированный оклад в месяц. Стоимость ресурса зависит от доли рабочих дней, фактически отработанных на проекте, в общем числе рабочих дней соответствующего календарного месяца.

#### 2.2.2. Исполнители (Contractor)

Внешние физические лица, работающие по одному из двух договорных режимов:

- **ГПХ** — договор гражданско-правового характера; налоги/взносы обычно удерживает заказчик.
- **НПД** — режим самозанятого; исполнитель самостоятельно уплачивает налог на профессиональный доход.

Форма оплаты — почасовая ставка. Стоимость = часовая ставка × фактическое число часов.

#### 2.2.3. Подрядчики (Subcontractor)

Сторонние юридические или физические лица, выполняющие фрагмент работ по договору подряда. Поддерживаются две схемы ценообразования:

- Фиксированная сумма договора.
- Почасовая ставка × количество часов.

#### 2.2.4. Оборудование (Equipment)

Технические средства, предоставляемые организацией заказчику на возмездной основе. Ценообразование поддерживается в трёх режимах: за месяц, за час, за минуту. Также учитывается количество единиц оборудования.

### 2.3. Производственный календарь

Система использует собственный производственный календарь, опубликованный в виде JSON-файлов по годам в каталоге `calendar/` (файлы `calendar_2025.json`, `calendar_2026.json`). Каждый день помечен одним из трёх статусов:

- `work` — рабочий день;
- `weekend` — выходной;
- `holiday` — праздничный (нерабочий).

Формат файла:

```json
{
  "year": 2025,
  "calendar": {
    "1": { "1": "holiday", "9": "work", "11": "weekend" },
    "2": { "1": "weekend" }
  }
}
```

При отсутствии файла-календаря или неизвестном статусе дня применяется резервное правило: рабочий день — это любой день с понедельника по пятницу (`weekday < 5`).

### 2.4. Расписание занятости сотрудников

Дополнительно поддерживается модуль расписания (модель `EmployeeSchedule`): для каждого сотрудника можно указать периоды, когда он недоступен для работы на конкретном проекте. Статусы:

- `work` — работает;
- `dayoff` — выходной / отпуск;
- `other_project` — занят другим проектом.

При расчёте число рабочих дней на проекте уменьшается на число дней из расписания со статусами `dayoff` и `other_project`, попадающих в период работы.

- Ф17. Агрегация общей себестоимости проекта.
- Ф18. Расчёт стоимости с учётом маржинальности.
- Ф19. Расчёт итоговой цены с учётом налоговой ставки.
- Ф20. Расчёт чистой прибыли проекта.

- Ф24. Формирование коммерческого предложения в Word.

- Ф28. Удаление записи расписания.

## Раздел 6. Архитектура системы

### 6.1. Общая архитектура

Система построена в классической трёхзвенной архитектуре:

1. **Уровень представления (клиент)** — браузер пользователя, отрисовывающий HTML-шаблоны, возвращаемые сервером, и выполняющий JavaScript-логику интерактивности.
2. **Уровень бизнес-логики (сервер приложений)** — Django-приложение, разделённое на модели, сервисные классы расчёта и представления (views).
3. **Уровень хранения данных** — реляционная СУБД PostgreSQL (prod) или SQLite (dev), а также файловая система (медиа, статические файлы, JSON-календари, шрифты).

### 6.2. Шаблон MVT (Model — View — Template)

Django-приложение построено по шаблону MVT, являющемуся вариацией MVC:

- **Model** — классы `Project`, `Employee`, `Contractor`, `Subcontractor`, `Equipment`, `Service`, `ProjectCost`, `ProjectResourceOverride`, `EmployeeSchedule` (файл `mainboard/models.py`).
- **View** — функции-представления в `mainboard/views.py` (более 2800 строк), обрабатывающие HTTP-запросы, вызывающие бизнес-логику и формирующие ответ.
- **Template** — HTML-шаблоны в каталоге `templates/` (базовый шаблон `base.html` + шаблоны страниц: `index.html`, `login.html`, `project_list.html`, `create_project.html`, `project_manage.html`, `gantt.html`, `generate_documents.html`, `profile.html`, `404.html`, `500.html`).

### 6.4. Ключевые сервисные классы (слой бизнес-логики)

#### 6.4.1. `ResourceType`, `PricingType`, `ContractType`, `EntityType`

Классы-перечисления, фиксирующие допустимые значения соответствующих атрибутов (тип ресурса, тип ценообразования, тип контракта, тип юридического лица). Размещены в `mainboard/views.py`.

#### 6.4.2. `ResourceCalculator`

Статический класс, инкапсулирующий алгоритмы расчёта стоимости отдельного ресурса:

- `calculate_employee_cost(...)` — расчёт стоимости сотрудника с учётом оклада, налога, маржи и доли отработанных дней;
- `calculate_executor_cost(...)` — расчёт стоимости исполнителя (ГПХ/НПД);
- `calculate_contractor_cost(...)` — расчёт стоимости подрядчика;
- `calculate_equipment_cost(...)` — расчёт стоимости оборудования с учётом трёх тарифов;
- `_count_business_days(start, end)` — подсчёт рабочих дней по JSON-календарю;
- `_working_days_in_month(ref_date)` — число рабочих дней в месяце.

#### 6.4.3. `ProjectCostCalculator`

Агрегирующий класс, принимающий список ресурсов и рассчитывающий суммарную себестоимость, стоимость с маржой, итоговую стоимость с налогом и чистую прибыль.

#### 6.4.4. `DocumentGenerator`

Класс, формирующий документы (коммерческое предложение, НМА) в форматах PDF (через `reportlab`), XLSX (через `openpyxl`) и DOCX (через `python-docx`). Включает собственные методы регистрации шрифтов DejaVu Sans, стилей абзацев и таблиц.

### 6.5. Взаимодействие компонентов (последовательность типового запроса)

1. Пользователь нажимает «Добавить сотрудника» на странице карточки проекта.
2. Браузер отправляет POST `/project/<id>/add_employee/`.
3. Django Middleware выполняет проверки (CSRF, аутентификация).
4. URL-диспетчер маршрутизирует запрос в `views.add_employee`.
5. Представление валидирует поля формы, создаёт запись `Employee` через ORM, сохраняет её в транзакции.
6. При обращении к карточке проекта (`project_manage`) запускается цикл по всем ресурсам: для каждого вызываются методы `ResourceCalculator` и агрегируются итоги.
7. Результаты передаются в шаблон `project_manage.html`, рендерится HTML и возвращается клиенту.

## Раздел 8. Математическая модель и формулы расчёта

Все формулы зафиксированы в файле `formulas.xlsx` и имеют уникальные идентификаторы. Ниже приведено их развернутое математическое описание.

### 8.1. Вспомогательные обозначения

- $S_m$ — месячный оклад сотрудника;
- $t$ — налоговая ставка в процентах;
- $m$ — маржинальность в процентах;
- $D_p$ — количество рабочих дней сотрудника на проекте;
- $D_m$ — общее количество рабочих дней в контрольном месяце;
- $r_h$ — часовая ставка;
- $H$ — количество рабочих часов;
- $F$ — фиксированная сумма договора;
- $c_{op}$ — операционная ставка оборудования;
- $q$ — количество единиц оборудования;
- $d_1$, $d_2$ — даты начала и окончания периода.

### 8.2. Формулы для сотрудников

**EMP-1. Стоимость сотрудника за месяц с учётом налога:**

$$C_{month} = S_m \cdot \left(1 + \dfrac{t}{100}\right)$$

**EMP-2. Себестоимость за период (с учётом доли отработанных дней):**

$$C_{cost} = C_{month} \cdot \dfrac{D_p}{D_m}$$

При этом $D_p$ вычисляется как количество рабочих дней в отрезке $[d_1, d_2]$ по производственному календарю (см. алгоритм 8.7), а $D_m$ — количество рабочих дней в контрольном месяце (по умолчанию — месяце даты начала работ, при недоступности календаря — 22).

**EMP-3. Итоговая стоимость сотрудника с учётом маржи:**

$$C_{final} = C_{cost} \cdot \left(1 + \dfrac{m}{100}\right)$$

### 8.3. Формулы для исполнителей (ГПХ/НПД)

**CONTR-1. Фиксированная оплата:**

$$C_{cost} = F$$

**CONTR-2. Почасовая оплата:**

$$C_{cost} = r_h \cdot H$$

**CONTR-3. Итог с налогом:**

$$C_{final} = C_{cost} \cdot \left(1 + \dfrac{t}{100}\right)$$

### 8.4. Формулы для подрядчиков

**SUB-1. Себестоимость (комбинированная):**

$$
C_{cost} = \begin{cases}
F, & \text{если pricing\_type} = \text{fixed} \\
r_h \cdot H, & \text{если pricing\_type} = \text{hourly}
\end{cases}
$$

**SUB-2. Итог с налогом:**

$$C_{final} = C_{cost} \cdot \left(1 + \dfrac{t}{100}\right)$$

### 8.5. Формулы для оборудования

**EQ-1. Месячная ставка по календарным месяцам (с округлением вверх):**

$$
N_{months} = \max\left(1,\ (y_2 - y_1) \cdot 12 + (M_2 - M_1) + [\,d_{day,2} \geq d_{day,1}\,]\right)
$$

$$C_{cost} = c_{op} \cdot N_{months} \cdot q$$

где $[\cdot]$ — индикаторная функция Айверсона, $y_i$, $M_i$, $d_{day,i}$ — год, месяц и день даты $d_i$.

**EQ-2. Почасовая ставка по датам:**

$$N_{days} = (d_2 - d_1)_{days} + 1$$

$$N_{hours} = N_{days} \cdot 24$$

$$C_{cost} = c_{op} \cdot N_{hours} \cdot q$$

**EQ-3. Поминутная ставка по датам:**

$$N_{minutes} = N_{days} \cdot 24 \cdot 60$$

$$C_{cost} = c_{op} \cdot N_{minutes} \cdot q$$

**EQ-4. Legacy-логика (даты не заданы):**

$$
C_{cost} = \begin{cases}
c_{op} \cdot H, & \text{type = hour} \\
c_{op} \cdot H \cdot 60, & \text{type = minute} \\
c_{op} \cdot \dfrac{D_p}{22}, & \text{type = month, если } D_p > 0 \\
c_{op}, & \text{иначе}
\end{cases}
$$

### 8.6. Формулы уровня проекта

**PRJ-1. Себестоимость проекта:**

$$C_{proj} = \sum\limits_{i=1}^{n} C_{cost,i}$$

где $n$ — число ресурсов, $C_{cost,i}$ — себестоимость $i$-го ресурса.

**PRJ-2. Стоимость проекта с маржой:**

$$C_{margin} = C_{proj} \cdot \left(1 + \dfrac{m_{proj}}{100}\right)$$

**PRJ-3. Итоговая стоимость с налогом:**

$$P_{final} = C_{margin} \cdot \left(1 + \dfrac{t_{proj}}{100}\right)$$

**PRJ-4. Чистая прибыль:**

$$\Pi = P_{final} - C_{proj}$$

### 8.7. Алгоритм подсчёта рабочих дней (VIEW-3)

```
Вход: start, end — даты, год за год загружаются JSON-календари
Выход: day_count — число рабочих дней в [start, end]

1. Если start или end не заданы, или end < start — вернуть 0.
2. Инициализировать day_count ← 0.
3. Инициализировать кэш календарей по годам.
4. Для каждой даты d от start до end (включительно):
    4.1. Загрузить (или взять из кэша) календарь на год d.year.
    4.2. Если календарь загружен и содержит статус для d:
         - если status == "work" → day_count ← day_count + 1.
    4.3. Иначе (fallback): если weekday(d) ∈ {0..4} → day_count ← day_count + 1.
5. Вернуть day_count.
```

**Дополнительно:** при расчёте сотрудника из `day_count` вычитается число рабочих дней, попадающих в расписание со статусами `dayoff` и `other_project`:

$$D_{effective} = \max\left(0,\ D_p - D_{unavailable}\right)$$

### 8.8. Налоговый множитель (VIEW-2)

$$k_{tax} = 1 + \dfrac{t_{proj}}{100}$$

Используется как единый коэффициент при агрегации всех ресурсов проекта.

### 8.9. Маржа ресурса в сводной таблице (VIEW-4)

$$C_{final,i} = C_{cost,i} \cdot \left(1 + \dfrac{m_i}{100}\right)$$

где $m_i$ — индивидуальная маржа $i$-го ресурса, задаваемая в `ProjectResourceOverride.resource_margin`.

## Раздел 9. Алгоритмы ключевых функций

### 9.1. Алгоритм расчёта стоимости проекта

```
Вход: project — карточка проекта
Выход: cost_price, final_price, net_profit

1. Инициализировать total ← 0.
2. Загрузить все активные ресурсы проекта: employees, contractors, subcontractors, equipment.
3. Загрузить переопределения (ProjectResourceOverride) в словарь overrides_map[(type, id)].
4. Загрузить расписание EmployeeSchedule со статусами dayoff/other_project.
5. Для каждого сотрудника e:
    5.1. Определить даты работ: из overrides_map или из модели.
    5.2. D_p ← count_business_days(start, end).
    5.3. D_un ← число недоступных рабочих дней по расписанию.
    5.4. D_eff ← max(0, D_p − D_un).
    5.5. D_m ← working_days_in_month(start).
    5.6. months_fraction ← D_eff / D_m.
    5.7. base_cost ← e.monthly_salary × months_fraction.
    5.8. total ← total + base_cost × k_tax.
6. Для каждого исполнителя c:
    6.1. Определить working_hours из override или модели.
    6.2. base ← c.hourly_rate × working_hours.
    6.3. total ← total + base × k_tax.
7. Аналогично для подрядчиков и оборудования (по их формулам).
8. cost_with_margin ← total × (1 + margin/100).
9. final_price ← cost_with_margin × (1 + tax_rate/100).
10. net_profit ← final_price − total.
11. Вернуть (total, final_price, net_profit).
```

### 9.2. Алгоритм генерации коммерческого предложения (PDF)

```
1. Зарегистрировать шрифты DejaVuSans / DejaVuSans-Bold (если доступны).
2. Создать буфер BytesIO и объект SimpleDocTemplate с размером letter.
3. Добавить логотип компании (если задан в company_settings).
4. Добавить заголовок «Коммерческое предложение».
5. Сформировать таблицу «Информация о заказчике».
6. Сформировать таблицу «Информация о проекте» (название, даты, налог, маржа).
7. Сформировать таблицу «Ресурсы проекта» с колонками: №, Название, Тип, Стоимость, Итого.
8. Сформировать таблицу итогов: себестоимость, маржа, налог, итоговая цена.
9. Собрать документ в буфер и вернуть BytesIO.
```

### 9.3. Алгоритм построения диаграммы Ганта

```
Вход: все записи EmployeeSchedule по активным сотрудникам.
1. Определить временной диапазон: min(start_date) — max(end_date) среди всех записей.
2. Построить сетку дней в пределах диапазона.
3. Для каждого сотрудника сформировать ряд полос:
    — status=work → зелёный
    — status=dayoff → серый
    — status=other_project → оранжевый
4. Разметить оси (даты по X, сотрудники по Y).
5. Отрисовать HTML-таблицу/SVG через шаблон gantt.html.
```

### 10.2. Сценарии использования (use cases)

**UC-1. Авторизация.** Пользователь открывает `/login/`, вводит логин и пароль, подтверждает форму. При успехе — редирект на `/project/`.

**UC-2. Создание проекта.** Пользователь нажимает «Создать проект», заполняет форму (название, заказчик, даты, налог, маржа), при необходимости сразу добавляет ресурсы.

**UC-3. Управление ресурсами.** На странице `project_manage.html` пользователь добавляет сотрудников, исполнителей, подрядчиков, оборудование через модальные окна; видит таблицу со значениями стоимости, обновляющимися после каждого изменения.

**UC-4. Переопределение параметров ресурса.** Внутри сводной таблицы пользователь изменяет период работ, количество часов, назначает услугу, вводит индивидуальную маржу; изменения сохраняются через асинхронный XHR-запрос на `/project/<id>/update_resource/`.

**UC-5. Формирование документов.** Пользователь переходит по ссылке `Generate documents`, выбирает формат (PDF/Excel/Word) и тип документа (КП/НМА). Система возвращает файл как HTTP-ответ.

**UC-6. Управление расписанием.** На странице `/gantt/` пользователь создаёт / удаляет записи `EmployeeSchedule`; изменения немедленно влияют на расчёт стоимости проектов.

**UC-7. Администрирование.** Администратор входит в `/scbp_admin_panel/` (кастомизированный Django-admin на базе django-unfold), где редактирует любую сущность напрямую.

### 10.3. Эргономика

- Цветовая палитра основана на корпоративном синем `#5858F6`.
- Типизированные формы с валидацией на стороне сервера.
- Сообщения пользователю через `django.contrib.messages`.
- Асинхронные обновления критических полей (налог, маржа, переопределения ресурсов) без перезагрузки страницы.

## Раздел 12. Генерация отчётных документов

### 12.1. Типы документов

1. **Коммерческое предложение (proposal)** — презентационный документ для заказчика. Содержит реквизиты заказчика, описание проекта, таблицу ресурсов, итоговую стоимость.
2. **Нормативно-методический акт (НМА)** — внутренний документ, фиксирующий состав работ и стоимость для учётных целей.

### 12.2. Форматы

Каждый тип документа формируется в трёх форматах:

- **PDF** — для печати и рассылки (библиотека `reportlab`, шрифт DejaVu Sans для поддержки кириллицы).
- **XLSX** — для редактирования и повторного использования в табличных процессорах (библиотека `openpyxl`, форматирование через `Font`, `Fill`, `Border`, `Alignment`).
- **DOCX** — для редактирования в MS Word / LibreOffice (библиотека `python-docx`, таблицы через `WD_TABLE_ALIGNMENT`, абзацы через `WD_ALIGN_PARAGRAPH`).

### 12.3. Класс `DocumentGenerator`

Принимает на вход:

- `project_data` — словарь с атрибутами проекта, списком ресурсов, итогами расчёта;
- `company_settings` — реквизиты компании-разработчика (наименование, ИНН, адрес, логотип);
- `font_path` — путь к файлам шрифтов.

Предоставляет методы:

- `generate_proposal_pdf() → BytesIO`;
- `generate_proposal_excel() → BytesIO`;
- `generate_proposal_word() → BytesIO`;
- аналогичные методы для НМА.

### 12.4. HTTP-отдача файлов

Представления `download_proposal_pdf`, `download_proposal_excel`, `download_proposal_word`, `download_nma_*` возвращают `HttpResponse` с MIME-типами:

- `application/pdf`;
- `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`;
- `application/vnd.openxmlformats-officedocument.wordprocessingml.document`.

И заголовком `Content-Disposition: attachment; filename="..."`.

## Раздел 13. Безопасность и авторизация

### 13.1. Аутентификация

Используется стандартный `django.contrib.auth`: модель `User`, backend `ModelBackend`, пароли хранятся как PBKDF2-хэши (`AUTH_PASSWORD_VALIDATORS` включает валидаторы сходства с атрибутами пользователя, минимальной длины, частых паролей и нечислового пароля).

### 13.2. Авторизация

Все представления, кроме `login_view`, защищены декоратором `@login_required`. Попытка обращения без авторизации приводит к редиректу на `/login/`.

### 13.3. Защита от сетевых атак

- **CSRF:** `CsrfViewMiddleware` — все POST-формы содержат скрытый токен `{% csrf_token %}`.
- **XSS:** автоматическое экранирование переменных в шаблонах Django.
- **Clickjacking:** `XFrameOptionsMiddleware` устанавливает заголовок `X-Frame-Options: DENY`.
- **SQL-инъекции:** исключены за счёт использования Django ORM (параметризованные запросы).
- **CORS:** `corsheaders.middleware.CorsMiddleware` — политика CORS для внешних клиентов API.

### 13.4. Сессии

Сессии пользователей хранятся в БД (таблица `django_session`), идентификатор передаётся через HTTPOnly-cookie. В prod-конфигурации должен быть включён `SESSION_COOKIE_SECURE = True` и использоваться HTTPS.

### 13.5. Секреты

- `SECRET_KEY` хранится в переменной окружения `DJANGO_SECRET_KEY` (в dev — есть дефолтное значение).
- Пароль БД в prod-конфигурации берётся из переменной окружения.

## Раздел 17. Потенциальный экономический эффект

### 17.1. Исходные данные для экономической главы ВКР

- Средняя трудоёмкость подготовки коммерческого предложения «вручную» (в Excel + Word): **3–4 часа работы менеджера**.
- Трудоёмкость с использованием SCBP: **10–15 минут**.
- Средняя оплата труда менеджера проектов в г. Москва: **120 000 ₽ в месяц**, что при 168 рабочих часах в среднем даёт стоимость часа ≈ **714 ₽**.

### 17.2. Экономия на одном документе

$$
\Delta T = 3{,}5\ \text{ч} - 0{,}2\ \text{ч} = 3{,}3\ \text{ч}
$$

$$
\Delta C_1 = 3{,}3 \cdot 714 \approx 2\,356\ \text{руб.}
$$

### 17.3. Годовой эффект

При среднем объёме 20 коммерческих предложений в месяц:

$$
\Delta C_{year} = \Delta C_1 \cdot 20 \cdot 12 \approx 565\,440\ \text{руб./год}
$$

### 17.4. Качественные эффекты

- Снижение числа ошибок в расчётах (исключение ручных формул в Excel).
- Единая методика расчёта по всему портфелю проектов.
- Оперативное планирование занятости персонала.
- Централизованная база знаний по проектам (архив).
- Повышение прозрачности экономики проектов для руководства.

### 17.5. Срок окупаемости

Если считать, что трудозатраты на разработку системы составили ≈ 400 человеко-часов одного разработчика средней квалификации (ставка 1 500 ₽/ч), себестоимость разработки:

$$
C_{dev} = 400 \cdot 1\,500 = 600\,000\ \text{руб.}
$$

$$
T_{ok} = \dfrac{C_{dev}}{\Delta C_{year}} = \dfrac{600\,000}{565\,440} \approx 1{,}06\ \text{года}
$$

Таким образом, система окупается примерно за 13 месяцев эксплуатации.

## Приложение Б. Полный список формул

| ID | Название | Формула |
|---|---|---|
| EMP-1 | Стоимость сотрудника за месяц с налогом | $C_{month} = S_m (1 + t/100)$ |
| EMP-2 | Себестоимость сотрудника за период | $C_{cost} = C_{month} \cdot D_p / D_m$ |
| EMP-3 | Итоговая стоимость сотрудника с маржой | $C_{final} = C_{cost} (1 + m/100)$ |
| CONTR-1 | Себестоимость исполнителя (фикс.) | $C_{cost} = F$ |
| CONTR-2 | Себестоимость исполнителя (почасовая) | $C_{cost} = r_h \cdot H$ |
| CONTR-3 | Итог исполнителя с налогом | $C_{final} = C_{cost} (1 + t/100)$ |
| SUB-1 | Себестоимость подрядчика | fixed или $r_h \cdot H$ |
| SUB-2 | Итог подрядчика с налогом | $C_{final} = C_{cost} (1 + t/100)$ |
| EQ-1 | Оборудование: месяц | $C = c_{op} \cdot N_{months} \cdot q$ |
| EQ-2 | Оборудование: час | $C = c_{op} \cdot N_{hours} \cdot q$ |
| EQ-3 | Оборудование: минута | $C = c_{op} \cdot N_{minutes} \cdot q$ |
| EQ-4 | Оборудование: legacy | см. 8.5 |
| PRJ-1 | Себестоимость проекта | $C_{proj} = \sum C_{cost,i}$ |
| PRJ-2 | Стоимость с маржой | $C_{margin} = C_{proj} (1 + m/100)$ |
| PRJ-3 | Итоговая стоимость | $P_{final} = C_{margin} (1 + t/100)$ |
| PRJ-4 | Чистая прибыль | $\Pi = P_{final} - C_{proj}$ |
| VIEW-1 | Календарные месяцы | $N_{months} = \max(1, \ldots)$ |
| VIEW-2 | Налоговый множитель | $k_{tax} = 1 + t/100$ |
| VIEW-3 | Рабочие дни | через JSON-календарь |
| VIEW-4 | Итоговая стоимость ресурса | $C_i = C_{cost,i}(1 + m_i/100)$ |
